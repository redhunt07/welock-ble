# Troubleshooting

All the failures below were observed while reverse-engineering the official app
and while bringing this integration up against real hardware.

## Configuration

### "Cannot reach the WeLock cloud" / DNS failures

If the host cannot resolve `clientapi.welock.com.cn`, check the DNS of the Home
Assistant host (`ha dns info` on Home Assistant OS) and any VPN/proxy in front of
it. A stale global HTTP proxy on the host also breaks the login: clear it
(`ha> network info` / system settings) and retry.

### "Wrong credentials"

* Use the phone in international format with digits only.
* The password is sent verbatim: check for trailing spaces or a password manager
  autofill.
* If the app still works but HA does not, try the WhatsApp login method: it is a
  different endpoint and does not involve the password.

### "Wrong or expired code"

* A `WL_XXXXXXXX` code is single-use: request a new one and send it to the bot
  before confirming.
* The bot must answer `OK` before the exchange; an "invalid message" reply means
  the code was mistyped or already spent.
* If you typed a code generated by the app, make sure it has exactly eight
  characters after `WL_`.

### "No locks on this account"

The account is valid but has no lock paired. Pair the lock in the WeLock app
first.

## Bluetooth

### "the lock refused to open" / status 00

* The cloud frame does not match the live challenge. Enable debug logs: the
  challenge, the derived `randomFactor` and the returned frame are logged. If
  `randomFactor` looks like `0x5555`-ish, bytes 0–1 of the challenge were used
  instead of bytes 2–3.
* `randomFactorData` must be omitted. A non-null value makes the server return a
  null token and the lock refuses the frame.
* `deviceName` must equal the lock's advertised name exactly.

### `BleakGATTProtocolError(UNLIKELY_ERROR: 14)`

* The write was sent without response or exceeded the ATT payload. The
  integration always writes with response and chunks at 20 bytes; if it still
  happens, the adapter is dropping the link: retry (the integration retries up to
  five times) or move the adapter/proxy closer.
* On Linux, `sudo systemctl restart bluetooth` clears stale BlueZ state.

### `[org.bluez.Error.InProgress]`

Another process is scanning or connecting. Stop `bluetoothctl` scans, close the
phone app, and retry.

### "device not found / removed from BlueZ"

The lock was not in the adapter cache. It must be in range and advertising. With
an ESPHome proxy, check that the proxy sees the lock (its log lists discovered
devices) and that active connections are enabled.

### The lock never answers the challenge

* The auth write was not acknowledged (see above).
* The connection was opened by another central: the WeLock app holds the link
  while its lock screen is open.
* Signal strength: the lock advertises at low power; −90 dBm and worse is
  marginal for some adapters.

### The second command on the same connection is rejected

Expected. The lock accepts one authentication per connection; the integration
reconnects for every command.

## Cloud

### HTTP 403 on `Command/UnLock`

The WeLock WAF rate-limits rapid unlock calls (observed after ~30 requests within
a minute). The integration paces requests; if you hit it from the probe tool, wait
a minute or lower the polling frequency.

### `{"code":1002}` on the login

Generic "not successful". Usually a wrong route segment (must be `welock`) or a
wrong identifier. The integration always uses the correct segment.

### `{"code":3003}` on `MessageLogin`

The WhatsApp code was not confirmed by the bot, or was already spent. Request a
new one.

### Token expires frequently

The cloud invalidates the token when the same account logs in elsewhere (for
example, another Home Assistant instance or a script that logs in with the
password). Use one instance, and let the entry refresh its token instead of
logging in manually.

## Home Assistant

### The integration does not appear in the list

* Check that `custom_components/welock_ble/manifest.json` exists and that you
  restarted Home Assistant after copying it.
* Look for `welock_ble` in *Settings → System → Logs*.

### Entities are unavailable after a restart

The entry failed to set up: check the logs for `ConfigEntryAuthFailed` (reauth
needed) or `ConfigEntryNotReady` (cloud unreachable). The device page offers
*Re-authenticate* when relevant.

## Collecting a good report

1. Enable debug logging for `custom_components.welock_ble`.
2. Reproduce the failure.
3. Download diagnostics (*Devices & Services → WeLock BLE → Download
   diagnostics*) — credentials are redacted.
4. Include the debug lines around the failed command (challenge, randomFactor,
   frame, reply) in the issue.
